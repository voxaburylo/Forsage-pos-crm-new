# Випуск Форсаж CRM

## Робоче середовище

Веб та серверний API працюють на https://forsage-pos-crm-new-web.vercel.app.
Маршрути /api/v1 обслуговує api/index.ts із кодом server/src.
Render виведений з експлуатації; render.yaml — залишена конфігурація старого
розгортання, а не адреса робочої каси.

Головна база магазину — локальна SQLite. Supabase zuhanlspejgizjbwbnda
містить серверну копію для вебперегляду. Цей порядок випуску не дозволяє
зворотний запис хмари у локальні залишки, накладні, ціни чи оплати.

## Перевірки перед публікацією

1. Звірити git status, віддалений репозиторій, склад змін і контрольний запис
   останнього пакета. Робочі бази, вкладення, паролі, службові ключі та .env
   не повинні потрапити до Git або завантаження Vercel.
2. На Node 24 виконати pnpm verify та pnpm build, перевірити desktop-збірку,
   відповідні Electron/UI-сценарії й упакований файл. Результати фіксувати
   окремо від факту встановлення та публікації.
3. Конкурентні серверні сценарії запускати командою pnpm --filter server
   test:postgres лише з FORSAGE_TEST_POSTGRES_URL на окремій порожній локальній
   базі forsage_concurrency_test або її тестовому суфіксі. Робочі .env та
   DATABASE_URL не використовувати для тестових записів.
4. Для змін схеми потрібні окреме погодження, перевірена резервна копія,
   попередня перевірка сумісності й звірка бізнес-підсумків після застосування.
   Міграції не запускаються автоматично від git push.

## Послідовність сумісного оновлення

1. Спочатку застосувати лише погоджені додаткові зміни серверної схеми.
   Старий сервер має продовжувати працювати з ними.
2. Опублікувати сервер і веб через наявний репозиторій. Push може запустити
   Vercel автоматично, тому його не можна робити раніше обов'язкової міграції.
3. Дочекатися успішного GitHub Verify та production-розгортання потрібного
   commit. Перевірити /api/v1/health, доступ до бази та авторизоване читання
   контрольного знімка. Один HTTP 200 або успішний push не доводить готовність.
4. Підготувати й перевірити локальний EXE окремо від установленого файла.
5. Коли програма закрита, встановити підготовлений EXE перевіреним установником.
   Якщо вона відкрита — залишити збірку підготовленою, не завершувати процес примусово.
6. Оновити наявний архів менеджера тією самою сумісною версією, без робочої бази,
   секретів і створення другого головного сховища. Другий ПК вважається
   перевіреним лише після фактичного спільного випробування.

Для пакетів 52–58 обов'язкова міграція
supabase/migrations/20261010185339_supplier_catalog_ownership_proof.sql:
три службові поля, обмеження та частковий індекс підтверджень прайсів.
Станом на 11.10.2026 до випуску потрібен окремий дозвіл на її застосування.
Новий сервер відмовляє у зміні прайсу до запису, якщо полів ще немає;
це аварійний захист, а не заміна правильного порядку випуску.

## Збірка без перезапису робочого EXE

На цьому ПК ярлик «ФОРСАЖ — КАСА» веде на
apps/desktop/release/Forsage-0.1.0-portable.exe. Звичайний desktop dist
пише в цей каталог, тому для підготовки оновлення потрібен окремий staged.

Після перевірок, із кореня репозиторію; кожен крок виконувати лише після
успішного завершення попереднього:

```powershell
pnpm --filter desktop exec cross-env FORSAGE_DESKTOP_BUILD=1 pnpm --filter web build
pnpm --filter desktop build
node apps/desktop/scripts/embed-renderer.cjs
node apps/desktop/scripts/build-info.cjs
node apps/desktop/scripts/verify-build.cjs
pnpm --filter desktop exec electron-builder --win portable --x64 "--config.directories.output=release/staged" --publish never
node apps/desktop/scripts/verify-package.cjs apps/desktop/release/staged/win-unpacked/resources/app.asar
Get-FileHash apps/desktop/release/staged/Forsage-0.1.0-portable.exe -Algorithm SHA256
```

Перед заміною перевірити резерв локальної бази та сумісність клієнта/сервера.
Передати установнику фактичний SHA256 щойно перевіреного файла:

```powershell
node apps/desktop/scripts/install-release.cjs <SHA256>
```

Установник перевіряє закриття програми та контрольні суми, замінює EXE
атомарно й зберігає попередній у
%LOCALAPPDATA%/Forsage/old-builds/Forsage-before-update.exe.
Нові папки або дублікати ярликів на робочому столі не потрібні.

Ідентичність випуску перевіряти за build-info: releaseId, contentHash,
sourceCommit, sourceDirty та SHA256 EXE. Номер schema_migrations показує
версію схеми, але не підтверджує свіжість програми: багато виправлень
не змінюють схему.

## Безпечний відкат

Повернення старого EXE не означає відновлення старої робочої бази.
Не підміняти поточні продажі й залишки резервом заради відкату програми.

Старий сервер може не розуміти нові докази перенесення прайсів та обмеження
порядку операцій. Після появи нових операцій простий revert сервера не
вважається безпечним. Зупинити відповідні записи, звірити підтвердження
і випустити сумісне виправлення або перевірений сумісний попередній код.
Додаткові службові колонки при цьому не видаляти.
Якщо відновлення установником не вдалося, зберегти recovery-файли й журнал;
не повторювати заміну автоматично.

## Змінні середовища

Публічні VITE_SUPABASE_URL та VITE_SUPABASE_ANON_KEY не замінюють серверних
прав доступу. Службові ключі, DATABASE_URL і JWT_SECRET зберігаються лише
в захищених налаштуваннях сервера або локальних .env, не в VITE_* і не в Git.

Веб використовує API того самого домену. Desktop renderer потребує
дозволеної HTTPS-адреси API; перевірку виконує verify-web-env.cjs.
Старі .onrender.com не можна повертати в робочі налаштування.

Архівна інструкція PM2: docs/archive/DEPLOY_pm2.md; для чинного випуску
вона не застосовується.
