# Пакет 95 — київські дати зарплатного API та актуальна перевірка аналітики

## Підтверджена причина

Старий серверний шлях зарплати за відсутності явної дати використовував
`toISOString()`: UTC-день і UTC-місяць. Улітку між 00:00 та 03:00 за Києвом,
узимку між 00:00 та 02:00 операція без дати могла отримати попередній день.
На межі місяців та років зведення без явного періоду вибирало попередній
місяць. Це відтворено на ізольованому маршруті, а не на базі магазину.

Новий тест до виправлення: 5 failed / 5 passed. Помилки відповідають
саме різниці UTC/Kyiv, без помилок підготовки чи таймаутів.

## Мінімальне виправлення

- GET `/salary/summary` і `/salary/commission-preview` використовують
  наявний `kyivDateKey()` для місяця за замовчуванням.
- POST `/salary` обчислює київське «сьогодні» один раз для узгодженого
  місяця та дня, якщо клієнт їх не передав.
- Явно передані дати й періоди збережені без змін. Якщо задано лише
  `work_date`, період, як і в локальному API, залишається поточним:
  нове бізнес-правило не вводиться.
- SQL, схема, права, суми, повтори запитів і політика виплат не змінені.
  Історичні операції не переписувалися.

Код: `71c846c`. Це серверна правка, сумісна з встановленим EXE пакета 93.
Новий EXE не потрібен; його точні хеші та архів менеджера описані в
[пакеті 94](PRODUCT_READINESS_STAGE94_2026-10-12.md).

## Перевірки

- 10 нових тестів маршрутів: літня та зимова північ до/після межі,
  перехід місяця/року, явні історичні дати, незалежний період.
- Разом з історією зарплати, захистом власника й businessDate: 21/21 PASS.
- Server typecheck та API typecheck: PASS.
- Окремий повтор десяти нових тестів із часовими поясами сервера
  `UTC` і `America/Los_Angeles`: 10/10 PASS у кожному. Результат
  визначається Europe/Kyiv, а не середовищем сервера.
- Реальний клієнт Supabase у новому тесті працює через підставний fetch
  тільки з `database.invalid`. Тести перевіряють параметри запиту,
  включно з tenant_id; POST отримує підставну транзакцію.
- Чистий release-worktree fast-forward до `71c846c`, без відкладених
  файлів постачальників. Повний серверний прогін: 105/105 файлів,
  1 886/1 886 тестів PASS, 513,26 с. Server build та API typecheck
  на цій самій чистій копії: PASS.
- Обмежений скан 1 626 відстежуваних файлів за вісьмома відомими приватними
  значеннями й шаблонами секретів: збігів немає.

Застосована навичка Supabase: перевірено актуальний changelog і довідку
фільтра `eq`; SDK, API-виклики й схему не змінювали. Недоступний markdown
індекс замінено читанням офіційної HTML-сторінки. Верифікація відбулася
ізольованими запитами, без експериментів на робочому сервері.

## Виправлення перевірки аналітики

CI timeout відтворився локально на чистій копії. У пакеті 93 підпис KPI
уже уточнено до «Продажі після повернень», а сценарій усе ще очікував
«Продажі за вибраний період». Помилка була в очікуванні тесту, не у
виборі дати на екрані. Production-екран для проходження тесту не змінено.

Коміт `5eb5fcb` оновлює перевірку та посилює її: історичний день має інші
суми, тест перевіряє точні startDate/endDate запиту, значення поля, діапазон
на екрані, нові суми і відсутність старої виручки. Просто очікувати новий
підпис було б недостатньо. Всі 11 груп dashboard smoke пройшли локально.
Після цього послідовно перевірено набір web UI smoke з CI,
з тестовими адресами й ключами, на чистій копії.

Цей прогін виявив також старі очікування в payroll-action UI smoke:
виплата в історії вже показує від'ємний вплив на баланс працівника,
але тест очікував суму без знаку; для сторно очікував ASCII-дефіс
замість мінуса, який використовує спільна історія. Коміт `47be109`
коригує лише ці три очікування. Суми «Нараховано», «Виплачено», баланс,
незмінність вихідних записів та відсутність повторної операції перевіряються
як раніше. Повний payroll-action UI smoke пройшов; production-код
та збережені гроші не змінені. Решта прогону продовжена з цього місця.

Наступний старий fixture — stability UI — відкривав PayrollPage без
Router, хоча сторінка вже читає параметри маршруту. Коміт `98e88b8`
додає тільки MemoryRouter із явним тестовим періодом. Після виправлення
сценарій перевірив всі 451 записи, поступове відображення й розділення
локальних/зовнішніх резервних копій. Production-навігація не змінювалася.

Підсумок послідовного прогону після цих виправлень: всі 27 web UI smoke
скриптів із поточного CI пройшли. Раніше успішні скрипти не запускалися
заново після кожної зупинки; прогін продовжувався з виправленого місця.
Зокрема пройшли звіти, накладні, ревізія, повернення, замовлення, доступ,
картки, зарплата, шиномонтаж, ШІ-вхід та звичайна накладна без модального
зіставлення. Чеки з 1/2/18/45 позиціями мають точні суми та повний footer
у растрі; фізичного друку не було. Native-частина нового віддаленого
