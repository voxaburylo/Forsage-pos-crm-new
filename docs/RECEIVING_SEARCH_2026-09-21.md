# Пошук і навігація прихідних накладних — 21.09.2026

## Причина звернення й діагностика

У чорній скриньці за 21.09 знайдено 13 завершених викликів
`desktop:supply:list-suppliers`: усі `ok`, максимум 3 мс, помилок немає.
У робочій базі 35 постачальників, активних 21. Ліміт старого завантаження
200 не пояснює саме сьогоднішній випадок. Форма мала native select, а не
пошукове поле; також SQLite-пошук не враховував довільний регістр кирилиці.
Журнал не містить введеного користувачем запиту, тому точний невдалий пошук
відтворити по ньому неможливо.

## Зміни

- Вибір постачальника: пошук по всій базі за назвою, контактною особою або
  телефоном, сторінки результатів, клавіатура, повторення після помилки.
  Поточний вибір завантажується за ID незалежно від першої сторінки.
- Пошук постачальників у SQLite: Unicode case folding і literal substring,
  без трактування `%`/`_` як шаблону. У серверних OR-фільтрах текст екранується.
- Касир може прочитати список/картку постачальника для накладної; права
  редагування, злиття, видалення й боргів не розширено. Веб-режим тільки
  перегляду та обмеження TillOnly не змінювалися.
- У списку накладних є введення номера сторінки й кнопка «Перейти».
  Сторінка, статус і пошук зберігаються в URL та sessionStorage; повернення
  з деталей/редагування не скидає їх. Зміна фільтра скидає на першу сторінку.
- Пошук за назвою, артикулом або штрихкодом товару застосовується до всієї
  історії до COUNT/LIMIT. Кілька відповідних рядків не дублюють накладну.
  Локальні незбережені чернетки шукаються в актуальному draft store;
  старий запис тієї ж чернетки виключається з результатів.
- Стабільне сортування з ID, захист від запізнілих відповідей, повтор після
  помилки, корекція сторінки після зменшення кількості документів.

## Перевірки та межі

- Нові unit-тести локального SQL, чернеток, стану списку й серверного
  HTTP-запиту з реальним Supabase query builder (мережа замінена fixture).
- `node apps/web/scripts/invoice-search-ui-smoke.mjs`: реальні компоненти
  React у Chromium, синтетичні дані, зовнішні запити заблоковані. Перевірені
  сторінки/повернення/фільтри, зникла остання сторінка, пошук постачальника
  поза першою сторінкою, клавіатура без submit форми, stale response і retry.
- Пряме read-only виконання оновленого репозиторію на робочій SQLite:
  «ремень» — 7 накладних, «фільтр» — 11, частина назви «комф» — 1
  постачальник. Час приблизно 67–72 мс для накладних і 0,8 мс для постачальника.
  На цій перевірці виявлено й виправлено неправильне припущення про
  `draft_payload`: такого поля в локальній таблиці немає; миграція не потрібна.
- Окремо звірено серверну схему: у `supply_invoice_items` немає
  `deleted_at` (на відміну від SQLite). Серверний запит не звертається до
  цієї колонки; враховує видалення самої накладної й tenant обох зв'язків.
- Общая проверка: typecheck/lint и web/desktop suites прошли. В первом
  параллельном server suite упал V8/WASM worker тестовой среды; полный
  повтор `pnpm --filter server test -- --maxWorkers=1` прошёл: 305 тестов.
- Реального подключения к Supabase для нового поиска не выполнялось.
  Веб-накладные по-прежнему недоступны в read-only режиме магазина.
- Рабочие накладные, остатки, оплаты, пользователи не изменялись. EXE
  не заменён, публикации Git/Vercel не было. На ПК пока запущена сборка
  от 16.09.2026; установка накопленных исправлений — после закрытия программы.
