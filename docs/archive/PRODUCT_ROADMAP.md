## Roadmap (цінність для бізнесу / складність / ефект)

### CRITICAL — зробити перед/одразу після деплою
1. **Застосувати міграцію 109** (`109_reserve_skip_canceled_items.sql`) — скасовані позиції
   не триматимуть складський резерв. Цінність: висока (сток не «заморожується»),
   складність: хвилина. Код уже задеплоєний разом із нею.
2. **Смоук-чеклист після деплою** (AUDIT P0): 5 кроків — замовлення в магазині → заказ
   із чату → оплата → видача → прихідна накладна. Основа є: qa/-скрипти цієї сесії.
   Цінність: захист «хребта» бізнесу. Складність: низька (оформити). 

### HIGH — найбільша цінність для щоденної роботи
1. **[РЕАЛІЗОВАНО 11.06] Сторінка «Замовлення постачальникам»** — авто-PO створювались,
   але їх не було видно ніде. Тепер: вкладка під Постачальниками, список PO зі статусами,
   позиціями, відміткою «Отримано». Цінність: закриває розрив закупівельного циклу.
2. **Прогін «часткова передоплата → доплата на касі → видача»** (AUDIT P0) — критичний
   грошовий шлях, перевірити живцем по всіх каналах. Складність: година QA.
3. **[РЕАЛІЗОВАНО 11.06] Дубль телефону при швидкому створенні клієнта** — тепер
   автоматично підставляє існуючого клієнта замість глухого кута з помилкою.
4. **Зрозумілі помилки без техкодів** — [РЕАЛІЗОВАНО 11.06] тости більше не показують
   префікси типу `INSUFFICIENT_STOCK:`.

### MEDIUM — зручність і цілісність
1. **Об'єднати налаштування** в один розділ з під-вкладками (AUDIT P3). Цінність:
   власник знаходить будь-що за один захід. Складність: середня (перенесення UI).
2. **Viber-канал** — найреальніший новий канал продажів (Bot API безкоштовний, ~1 день
   роботи + токен від вас). WhatsApp — після рішення про провайдера (платно).
3. **Закриття замовлення з повністю скасованими позиціями** — зараз банер-підказка;
   можна додати кнопку «Скасувати замовлення» прямо в банер.
4. **Пагінація /core-returns і архів виплачених застав** — поки список короткий, не горить.
5. **Историчність себестоимості**: накладна оновлює purchase_price товару; для точного
   P&L по партіях колись знадобиться FIFO/середньозважена (зараз — остання ціна, ок для MVP).

### LOW — косметика і пізніше
1. Єдиний стиль порожніх станів/заголовків (AUDIT P3).
2. Мобільна ревізія другорядних екранів (налаштування, накладні).
3. Offline-перевірка PWA на прод-білді (dev без service worker блимає білим — у проді є precache).
4. Drawer: дві кнопки «Скасувати» рознесені текстом — можна ще й кольором/розташуванням.

## Аудит безпеки (2026-06-11, повний прохід)

- **SQL-ін'єкції: немає.** Усі raw-запити параметризовані ($N), supabase-builder безпечний.
- **XSS: знайдено і ВИПРАВЛЕНО** — `LabelPrintModal` вставляв назву/артикул/штрихкод товару
  в `innerHTML` основного документа без екранування (вектор: HTML у назві товару з
  імпортованого прайсу постачальника). Також доекрановано друк KPI-звіту. Решта друкованих
  шаблонів уже використовували `esc()`.
- **CSRF: неактуальний** — Bearer-токени в заголовку (без cookie-сесій) + CORS-whitelist.
- **Rate limiting: є** — 300 req/хв глобально, 10 спроб/год на логін.
- **Авторизація:** усі роутери під requireAuth, гранульований requireRole, tenant-ізоляція
  в запитах і RLS. Залишок: ключі в git-історії (ротація за власником).

## Аудит продуктивності на масштабі

- **100k–1M товарів: готово.** pg_trgm GIN-індекси на sku/name/oem/кодах постачальників/
  аліасах/VIN (міграція 068) + tsvector — пошук ILIKE працює по індексу. Пошукові
  запити з limit.
- **Списки:** товари/клієнти — серверна пагінація; замовлення — cap 500; core-returns —
  додано limit 500 (було без обмеження).
- **Десятки тисяч замовлень:** індекси по order_id/tenant_id є; списки обмежені.
- **Конкурентність:** продажі — pg-транзакції з FOR UPDATE і lock_timeout 2s; оплати —
  idempotency keys (Lock-Before-Work); резерви — атомарний RPC; застави — умовні UPDATE.
  Кілька одночасних кас безпечні.
- **Кілька вкладок:** POS-чек живе в пам'яті вкладки (без localStorage) — конфліктів немає;
  спірні операції вирішує сервер. Оновлення сторінки втрачає незбережений чек —
  компенсація: «Відкладені чеки» (F5).
- **Вузьке місце майбутнього:** count exact на великих списках і last-price собівартість
  (див. MEDIUM-5). Не блокує до ~100k записів.

## Комерційна готовність (погляд власника мережі)

**Сильніше за типові CRM автозапчастин:** core exchange (застава за серцевини) з обліком
боргів обох напрямків — рідкість у конкурентів; аналоги по тірах брендів; VIN-підбір;
авто-PO постачальникам із замовлень; Telegram-канал продажів; ПРРО+термінал з коробки;
офлайн-PWA каса.

**Слабкіше за конкурентів (черга на закриття):**
1. Один магазин/склад (tenant зашитий) — блокер для продажу рішення іншим компаніям.
2. Немає інтеграцій із прайс-агрегаторами (Avtopro, Exist API) — імпорт лише файлами.
3. Немає клієнтського кабінету/вітрини (тільки внутрішня CRM + Telegram).
4. Собівартість last-price (без партій FIFO) — для мережі потрібна точніша маржа.

**Що дасть конкурентну перевагу швидко:** Viber/WhatsApp-канали; СМС/месенджер-нагадування
«ваше замовлення приїхало» (вже є для Telegram); експорт у клієнтський прайс (XLSX є,
додати публічне посилання).

### Технічний борг (відомий, не блокує)
- `tenant_id` фіксований (MVP, один магазин) — переробити при другому магазині.
- Ключі Supabase в git-історії — ротація за власником.
- Redis локально відсутній — bullmq спамить ретраями в dev-лог (на проді є).
