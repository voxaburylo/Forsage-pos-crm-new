# Повторна перевірка — 11 вересня 2026

Google Диск відкладено. Під час початкового аудиту код програми та робочі документи не змінювалися.
SQLite читалася через readOnly-з’єднання в одній транзакції. Руйнівні сценарії
перевірено лише на тимчасових тестових базах. Реального друку не було.

## Підтверджені проблеми

   Backend `pos/shifts.ts:321` також приймає NaN як нуль через money().
   Крім того, closeShift ідентифікує ціль за касиром, не shift_id/operation_id.
   Відтворено: закрити A, відкрити B, повторити запит A — закривається B зі
   старою сумою. Потрібні сувора валідація, конкретна зміна і безпечний повтор.

2. **P1: аварії на запуску.** У desktop-errors.log за 2026-09-11 05:05 UTC:

## Результат перевірок і порядок ремонту

`pnpm verify` пройшов: TypeScript web/desktop/server, web lint, весь web-набір,
350 desktop і 253 server тести. Додаткові сценарії вище знайшли прогалини
покриття; успішні старі тести не означають відсутності помилок.

Порядок: захист закриття та платежів → діагностика crash → документальна
звірка старих залишків → пошук/аванси замовлень → окремі партії друку.

Реальні два ПК по LAN та принтери не тестувалися. Ремонт, push і перескладання
EXE у цьому етапі не виконувалися. Створено лише цей звіт.

## Ремонт після підтвердження користувача

- Закриття передає конкретний shift_id через UI, preload, IPC та LAN. Результат
  і fingerprint зберігаються в одній транзакції зі зміною й завданням резервування.
  Повтор після перезапуску не закриває наступну зміну; змінений повтор відхиляється.
- Суми відкриття, звірки, закриття, ручних касових операцій і авансів перевіряються
  як цілі безпечні копійки. Невідомий спосіб оплати відхиляється до запису.
  Касиру перевіряється фактичний баланс ще раз на локальному backend; велика
  розбіжність у власника/адміністратора потребує пояснення.
- Форма закриття захищена від порожнього Enter, одночасних натискань, старих
  відповідей і помилки завантаження. Поля та закриття вікна блокуються на час
  запису. Помилка зарплатного звіту більше не показується як нульовий борг.
- Неоцінені чернетки приймають повторні аванси, не втрачаючи статус чернетки.
  Підтримані старі неоцінені записи зі статусом new. Оцінений/повністю сплачений
  або повністю знижений заказ не отримує дозвіл на переплату через status=lead.
  Фіскальні аванси цим каналом, як і раніше, заблоковані.
- Пошук замовлень/клієнтів у касі використовує forsage_lower для кирилиці;
  символи % та _ шукаються буквально. Список читає позиції одним пакетним
  запитом, а не окремим на кожне замовлення. Пагінація перевіряється на NaN,
  Infinity, дробові та від’ємні значення.
- Відновлення інтерфейсу має один цикл: початкове завантаження, crash та
  повтори більше не запускають паралельні load/reload. При закритті вікна
  таймер скасовується, повторні crash обмежені. Причина нативних аварій
  -2147483645 все ще НЕ встановлена; це виправлення координації, не гарантія
  усунення аварії GPU/Audio Service.
- Різні партії етикеток не зливаються. Однакові незавершені запити об’єднуються
  за HTML і параметрами; різні виконуються по черзі. Черга обмежена, параметри
  копіюються. У діагностиці є кількість етикеток, час рендеру, спулера і черги.

### Робочі залишки: тільки діагностика

Звірка в readOnly-транзакції підтвердила 326 розходжень, 310 з них мають
проведену, невидалену ревізію, кількість якої збігається з журналом руху,
але не з карткою. Для 308 із цих 310 дата картки старіша за рух. Ще 15 рухів
мають проведені продажі й старішу дату картки; один рух — старий stock_rebase.
У трьох випадках існує пізніша проведена ревізія, тож автоматично брати останній
рух як остаточний залишок особливо небезпечно. Невідомих методів/некоректних сум
у наявних order_payments не знайдено.

Робоча БД НЕ змінювалася. Перелік для контрольованого відновлення:
`C:\Users\neo\AppData\Local\Forsage\backups\Stock-review-2026-09-11.json`.
Відтворювана команда:
`node apps/desktop/scripts/review-stock-documents.cjs ABSOLUTE_DB_PATH ABSOLUTE_NEW_REPORT.json`.
Скрипт не мігрує БД, не коригує товар і не перезаписує існуючий файл звіту.
Історичні кількості потребують окремого узгодження, копії БД та перевірки всіх
документів/фактичного складу перед зміною.
