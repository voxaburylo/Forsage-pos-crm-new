# Пакет 16 Передача видалених виплат і руху каси

04.10.2026. Виправлено наявну передачу локальної зарплати та касових операцій.
Код, перевірки й службовий EXE готові. Робочий EXE, база магазину,
Supabase, GitHub та Vercel не змінені. Нових кнопок і можливостей немає.

## Підтверджені проблеми

Сервер повертав успіх для видалення відсутньої виплати, не зберігаючи
факту видалення. Створення зарплати й касового запису не перевіряло журнал
видалень. Запізнілі повідомлення могли повернути вже скасовані записи.

Повтор касової операції з іншою сумою мовчки приймався через
ON CONFLICT DO NOTHING. Дробові копійки округлювалися, а невідомий тип
касового запису міг перетворитися на внесення.

П'ять початкових тестів відтворили неправильну поведінку до виправлення.
Це не доказ причини конкретної минулої розбіжності в магазині:
історичні записи цього разу не звірялися й не виправлялися.

## Що змінено

- Видалення з локальної бази передає незмінний знімок первісної ручної
  виплати, включно з її касовою операцією. Сума й дата не вигадуються.
- Старий невідправлений запис видалення доповнюється лише з локального
  видаленого рядка з тим самим ID, магазином і часом видалення.
  Це читання узгодженого знімка, без зміни бази або збереженої черги.
- Сервер може прийняти видалення раніше за створення, якщо наявні повні
  реквізити. Для невідомого старого ID без реквізитів повертається явна
  вимога копії, а не помилкове підтвердження успіху.
- Видалення зарплати й її касового запису та обидві позначки видалення
  записуються в одній транзакції. Помилка повертає весь стан назад.
- Повторне створення не відновлює видалений запис. Повторне видалення
  не змінює первісну позначку часу й не видаляє іншу касову операцію.
- Спільні транзакційні блокування беруться в порядку зарплата, потім каса.
  Вони захищають також ID, рядок якого ще не встиг надійти.
- Автоматичні нарахування залишаються захищеними від видалення. Чужий
  магазин, інший зв'язок або невідповідна сума спричиняють конфлікт.
- Касова копія перевіряє цілу суму в копійках, тип, магазин зміни й
  працівників, дату та реквізити. Повтор активного запису звіряється
  повністю; жодного округлення, повторної видачі чи переписування суми.
- Правило локальної закритої зміни не послаблено. Копію вже виконаного
  раніше скасування можна передати пізніше, коли зміна на сервері закрита.
  Окремо внесені власником кошти не скасовуються разом із виплатою.

Для давніх касових повідомлень без виконавця збережено попередній
резервний вибір облікового запису передачі; достовірне історичне авторство
для таких повідомлень цей пакет не вигадує.

Використано наявний sync_deletions. Нових таблиць, прав і міграцій немає.
Належність працівника перевіряється за захищеними app metadata, не user metadata.
Порядок блокувань і межі транзакцій звірено з
[документацією PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).
Переглянуто [актуальні зміни Supabase](https://supabase.com/changelog);
використання ltree, pgcrypto чи нових API до цього виправлення не додавалося.

## Перевірки

Додано 92 сценарії: 80 серверних на ізольованому PGlite і 12 локальних
на SQLite. Перевірено всі шість порядків створення каси, створення зарплати
й видалення, повтори, відсутні залежності, конфлікти, чужі записи,
автоматичні нарахування, закриті зміни й відкат після помилки запису.

Повні набори пройшли:

- Desktop 126 файлів, 1164 тести.
- Web 139 файлів, 1363 тести й один давній пропущений.
- Server 89 файлів, 903 тести, послідовний прогін без аварії V8/WASM.
- Разом 3430 успішних тестів; 92 з них додані в цьому пакеті.
- Typecheck web, desktop, server і API; lint web; збірки server, web,
  desktop; diff check і перевірка складу ASAR.
- Окремий Electron запуск із тестовою базою: виплата 100 копійок,
  видалення, збереження касового підсумку, повторне відкриття бази,
  доповнення старого повідомлення в режимі лише читання.
  Повторено для зібраного ASAR, без принтерів і робочої бази.

Перший Electron тест зупинився на порівнянні звичайного об'єкта з рядком
SQLite без прототипу. Реквізити були однакові. Порівняння уточнено до
JSON, який фактично передається; обидва повторні запуски пройшли.
Перший локальний тест також мав неправильну передумову про fund_source
у createSalary; його виправлено на окреме фактичне внесення власника.
Робочий API для цього не розширювався.

Залишаються давні попередження збірки про великі JS частини й змішані
імпорти та попередження React у серверному рендері тестів. Їх не приховано.
PGlite перевіряє транзакції й порядки доставки, але не замінює навантажувальний
тест двох одночасних підключень до живого PostgreSQL.

## Що ще не виконано

- Установлення EXE і публікація серверної частини. Одне лише оновлення
  EXE не встановлює серверний захист цього пакета.
- Міграція пакета 14 у живій базі залишається невиконаною.
- Раніше помилково підтверджені видалення й старі неправильні копії
  потребують окремої звірки. Автоматичної чистки історії немає.
- Випробування на двох фізичних ПК залишається відкладеним.
- Наступний пункт погодженого плану: продані товари, пошук, дата,
  продавець та узгодженість підсумків локальної і вебкопії.
