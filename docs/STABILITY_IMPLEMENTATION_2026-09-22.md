## 1. AI-накладні без тривалого блокування головного потоку

- Blackbox старої збірки показав операцію створення AI-накладної 17 494 мс
  із затримкою головного потоку 14 912 мс.
- Повторна Unicode-нормалізація всього каталогу для кожного нового товару
  замінена індексом, обмеженим однією транзакцією. Нові позиції додаються
  в індекс, тому наступний рядок бачить уже створений товар.
- Створення відбувається в окремому worker. Записи документа, товарів і
  підтвердження операції залишаються атомарними. Worker-запити послідовні;
  повтор із тим самим ID перевіряє повний початковий payload.
- Не змінено правила зіставлення, ціноутворення, категорій та нульового
  залишку нового товару до проведення. Порожня робоча база при втраті файлу
  не створюється.
- Перевірений compiled Electron сценарій: каталог 15 000 товарів, 100 нових
  рядків по 98 шт; 1 281 мс, максимальна затримка heartbeat 32 мс.

## 2. Друк: чесний результат і контроль ручного повтору

- Перед надсиланням зберігається стан спроби для конкретного принтера.
  Якщо програма впала або результат невідомий, наступний друк потребує
  явного підтвердження після перевірки паперу/черги. За замовчуванням — скасування.
- Невдача підготовки макета відрізняється від помилки після надсилання.
  Помилка перевірки черги після надсилання завжди зберігає невизначеність,
  навіть коли текст містить «принтер не готовий».
- Локалізація не перетворює невідомий результат на твердження «не надруковано».
  Автоматичного повтору чи автоматичного видалення завдань зі спулера немає.
- RAW helper правильно отримує числовий ID Windows-завдання; перевіряє
  початок/завершення сторінки й документа. Етапи та ID записуються в blackbox.
- Прийнято Windows не означає фізично надруковано. У довговічному стані спроб
  немає HTML чека, переліку покупок, клієнта чи паролів.
- Черги POS-58 та POS-80 незалежні; перенаправлення чека на етикетковий
  принтер не додано.

## 3. Зарплата без обрізаної історії й підсумків

- Локальний API читає послідовні сторінки з однозначним сортуванням за датою
  та ID. Інтерфейс отримує всю історію, показує спочатку 50 рядків і дозволяє
  розкрити решту. Підсумок не залежить від кількості видимих рядків.
- Серверний список має tenant-фільтр, валідацію сторінки й ознаку наступної
  сторінки, обчислену до вилучення операцій власника. Порожня сторінка власника
  не обриває читання. Повтор тієї самої сторінки старим API дає помилку, а не цикл.
- Місячні й денні серверні підсумки читають усі операції сторінками за ID,
  а не лише першу відповідь, обмежену Data API. Помилка наступної сторінки
  не повертає часткову суму як повну.
- Перевірено 451 локальну операцію та 1 251 серверну операцію. Реальних
  виплат або перерахунку історичної зарплати не виконували.
- Серверна частина потребує майбутнього розгортання; зміна схеми БД не потрібна.

## 4. Менше фонових перевірок

- Порожня черга синхронізації перевіряється раз на 60 с, у прихованому вікні
  — 120 с; за наявності роботи — 10 с. Новий запис будить чергу; помилки
  мають поступове відкладення. Запит, що прийшов під час виконання, не губиться.
- За відсутності нової резервної копії перевірки відправлення мають паузу
  2 хвилини; втрата мережі не породжує щільний цикл повторів.
- Списки замовлень у касі не опитують базу у прихованому вікні; згорнута
  панель перевіряється рідше, початкове завантаження й лічильник збережені.
- Перевірка доступу/блокування сесії кожні 5 с залишена без змін.

## 5. Видимий стан резервування

- В існуючій картці налаштувань, без додаткового дубльованого розділу:
  остання локальна копія, копія після зміни, обидва Excel-файли, остання
  підтверджена зовнішня копія та її дата знімка/перевірки.
- Стан локальних файлів перевіряється в дозволених папках. Наявність одного
  лише шляху в БД більше не означає, що обидва Excel-файли доступні.
- Остання підтверджена зовнішня копія показується, навіть коли вона старіша
  за останні 20 змін. Нова непередана зміна не приховується за старим успіхом.
- Для старого EXE відсутність нових полів означає «стан не перевірено», а
  не вигаданий успіх. Помилка читання не показує повідомлення «копій немає».
- Копія для вебперегляду не прирівнюється до повного backup. Копія на тому
  самому диску не захищає від поломки диска. Нового хмарного провайдера чи
  Google Drive цей пакет не підключає.

## Що не можна вважати перевіреним

- Реальна одночасна робота двох фізичних ПК, обрив/відновлення LAN і
  аварійне переключення головного ПК — виключено користувачем.
- Фізична якість паперового чека/етикетки цим запуском не підтверджена;
  реальні принтери не отримували тестові завдання.
- Новий EXE встановлено, але робочий сеанс магазину автоматично не запускався;
  користувач відкриває програму своїм звичним ярликом.
- Нові серверні зміни не діють у вебверсії до публікації. Гарантії відсутності
  всіх майбутніх збоїв ці тести не дають.
