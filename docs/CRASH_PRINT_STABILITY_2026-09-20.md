# Збої інтерфейсу, звуку та друку — 20.09.2026

## Підтверджені факти

Перевірено 37 038 записів чорної скриньки за 20.09.2026. Робоча збірка від
16.09.2026, Electron 43.1.0, main fingerprint
`5c01f8389be77aa71d000847ffdef34b0876f6bcf460118ed9eb9f17197fa92f`.

- О 08:11 локального часу три аварії renderer за короткий проміжок;
  після вичерпання спроб відновлення main сам викликав app.quit().
- У наступному запуску три аварії AudioService і одна GPU. Код завершення
  -2147483645 сам по собі НЕ доводить несправність драйвера/відеокарти.
  Нативних дампів цього інциденту в каталозі звітів немає; Windows WER не
  дав додаткового стеку. Точну внутрішню причину старої аварії не встановлено.
- П'ять помилок підготовки HTML-чеків та три помилки TSPL-етикеток:
  PRINT_DOCUMENT_LOAD_FAILED / ERR_FAILED. Це до фізичної відправки принтеру,
  не доказ проблеми USB чи принтера. Парні console/command-end записи не
  рахуються повторними інцидентами.
- 27 недостатніх залишків користувач виключив із цього ремонту.

Базовий ізольований тест старого завантажувача сьогодні проходив: цей
переривчастий ERR_FAILED не відтворився стабільно. Зміни нижче усувають
вразливий механізм і додають захист, але не є доказом усунення всіх
можливих нативних аварій.

## Зміни

1. Windows запускає бізнес-інтерфейс і друк без апаратного прискорення.
   Sandbox, contextIsolation і заборона Node у renderer залишені ввімкненими.
   GPU-драйвер, Windows та налаштування фізичних принтерів не змінювались.
2. Відновлення renderer чекає завершення аварійного процесу. Якщо обмежені
   автоматичні спроби вичерпано, асинхронне вікно пропонує відновити тільки
   інтерфейс або закрити програму. Більше немає безумовного app.quit().
3. Після аварії нативного AudioService звук відключається лише до наступного
   запуску. Налаштування користувача не переписується. Каса не перезапускає
   пошкоджену звукову службу на кожне сканування. Оброблено resume rejection,
   suspended/closed стани, вимкнений звук та звільнення завершених вузлів.
4. Макети друку віддаються як локальна in-memory protocol response, без
   data-navigation/document.write, без тимчасових файлів клієнтських чеків.
   Окрема непостійна сесія не має cookies/сховища основної програми; CSP
   забороняє скрипти, зовнішню мережу та iframe. Шрифти системні, картинки
   вбудовані data/blob. Запис макета видаляється з пам'яті після навігації.
5. ERR_FAILED/ERR_ABORTED при ПІДГОТОВЦІ може повторитися один раз, до
   фізичного друку. Невизначена відповідь драйвера ніколи не запускає
   каскад повторної відправки; зміну параметрів дозволено тільки після
   явного Invalid printer settings. POS-58 / POS-80 залишені розділеними.
6. Чорна скринька окремо фіксує аварію print renderer, код навігації і
   підготовку макета. HTML, URL, дані чека, паролі й клієнти не записуються.

## Перевірки

- Повний pnpm verify: 590 web + 528 desktop + 301 server = 1419 тестів,
  typecheck усіх пакетів/API та lint без помилок. Додатковий тест зупинки
  відновлення після аварії: rendererRecovery 6/6 (разом 1420).
- Реальний Electron, окремий тимчасовий профіль: 1 → 1000 → 1 етикетка,
  звичайний та offscreen renderer, 4+ МБ UTF-8 макет, printToPDF, кирилиця,
  заборона скриптів і Node.
- Реальний растровий чек 384 dots / 203 dpi, TSPL dry-run із перевіркою,
  що бітмап містить надрукований текст/графіку, а не порожній кадр.
- Примусово аварійно завершено лише тестовий renderer: відновився, головний
  процес залишився живим. Бізнес-БД у цьому тесті взагалі не відкривається.
- Передача повідомлення про збій звуку через справжній sandboxed preload,
  включно з пізньою підпискою на подію.

## Межі

Робочі залишки, ціни, документи, чеки, кошти та SQLite не змінювались.
Фізичний друк не виконувався. Справжню паперову якість і цілу робочу зміну
слід перевірити після встановлення. EXE не замінюється без підтвердження
користувача; окремих нових папок програми не створювати.
