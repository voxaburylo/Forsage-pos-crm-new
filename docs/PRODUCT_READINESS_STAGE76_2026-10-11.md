# Пакет 76 Обработка большой очереди товаров

Дата: 11 октября 2026 года. Продолжение этапа 9 без новых функций и
изменений данных магазина. Исходный runtime `c2cfb0e`, исправление `df1ccbe`.

## Причина задержки и исправление

При запуске очередь ожидающих изменений товаров многократно фильтровалась
целиком для каждого товара. На 3000 строках тест зарегистрировал 3 003 000
чтений идентификатора. Новый проход использует уже имеющуюся сортировку SQL
и не меняет правила выбора: остаются самая новая версия и последняя явная
коррекция остатка, если новая версия является сохранением товара.

Выборка pending/failed, порядок пометки устаревших строк, поля UPDATE и
транзакция сохранены. Статусы sending/synced не затрагиваются. Группировка
по aggregate_id, включая её прежние ограничения между tenant/device,
сохранена; этот пакет не является изменением изоляции магазинов.

## Проверки

58 адресных тестов и проверка типов desktop успешны. В новых тестах есть
2000 детерминированных сравнений с прежним алгоритмом, удаление, несколько
коррекций, повреждённый JSON, небулевый признак stock_correction, пустой ID,
неизменность входа и ограничение числа чтений. До оптимизации проходили
24 из 25 новых unit-тестов: падала только проверка сложности.

Семь интеграционных сценариев используют SQLite исключительно в памяти,
реальные миграции и метод repository. Проверены неизменность бизнес-таблиц,
допустимые метаданные очереди, повторный запуск и полный откат после ошибки
в середине обновления. Независимый просмотр не нашёл блокирующих замечаний.

Замер выполнен обычным Electron на синтетической SQLite в памяти. На каждый
товар приходится четыре версии; остаются две. До изменения использован ASAR
кандидата 75, после — скомпилированный чистый код `df1ccbe`.

| Операций | До изменения | После изменения |
| --- | ---: | ---: |
| 4000 | 295,09 мс | 11,01 мс |
| 20 000 | 9020,37 мс | 64,32 мс |
| 40 000 | 36 052,15 мс | 120,31 мс |

Это однократные замеры отдельного метода, не полного холодного запуска EXE.
В них не входят чтение дисковой базы, распаковка EXE и запуск интерфейса.
Обе успешные проверки завершились с кодом 0; после выполнения сверены все
сохраняемые payload и результат повторного вызова. Первый запуск harness
был неправильно направлен на старую папку staged и не считается доказательством;
второй остановлен по внешнему тайм-ауту. После переноса импорта в app.whenReady
и явного compiled-dir получены указанные успешные результаты. Рабочая база,
сетевой обмен приложения и принтеры не запускались.

Внутренний таймер JavaScript не прерывает синхронный расчёт: зависший harness
нужно ограничивать внешним тайм-аутом процесса. При выходе старой успешной
проверки Electron зарегистрировал перезапуск сетевого подпроцесса; сам
тест завершился. Это не падение рабочей программы и не тест её сетевого обмена.

## Найденная следующая ошибка

Независимый сценарий производителя очереди выявил старый дефект: обычная
правка переписывает payload и дату прежней операции, сохраняя её sequence
и operation_id. После промежуточной коррекции остатка новая цена может
оказаться на более старом sequence и отбрасываться при запуске. Кроме того,
запоздалое подтверждение старого запроса может подтвердить новую, ещё не
отправленную правку. Эти ошибки не вызваны линейным алгоритмом.

Исправление завершено отдельно в пакете 77 с тестами реального производителя,
перезапуска и запоздалых ответов. Исторические очереди и облачные данные
автоматически не восстанавливаются; для них нужна отдельная сверка.
