# Захист і стійкість діагностики — 27.09.2026

Статус: код перевірено, НЕ встановлено / НЕ опубліковано.
Продовження погоджених технічного та AI-планів, без нових бізнес-функцій.
Робоча локальна база залишається єдиним джерелом істини; тестових записів у ній не було.

## Що відтворено й виправлено

1. Спільний серверний журнал приймав довільні вкладені об'єкти, сирі Error,
   відповіді провайдера та інтерполяцію повідомлень. Наявний список redact
   не охоплював кожну форму приватного payload.
   Тепер до серіалізації проходять тільки контрольовані метрики, коди,
   категорії помилок і відбитки кореляції. Текст документів, фото, URL,
   ключі та повні стеки з цих полів не записуються.
2. Стандартний короткий шлях Pino child обходив formatter прив'язок.
   Захист перевірено на справжньому Pino для child, grandchild та setBindings.
   Повідомлення чинних production-викликів перевіряються AST-тестом:
   літерал, без підстановки змінних. Два динамічні повідомлення виправлено.
3. Локальний журнал серіалізував context до захисного try.
   Цикл або BigInt могли кинути новий виняток під час фіксації первинної помилки.
   Підготовка даних тепер усередині захисту, context обмежений відомими полями.
4. «Чорна скринька» могла рекурсивно обходити циклічну помилку або запускати
   getters / toJSON / перетворення вкладеного об'єкта в текст.
   Обхід обмежений глибиною та відвіданими об'єктами; сторонні аксесори
   не викликаються. Для штатного Error.stack у Node 24 додано окремий
   захищений шлях, який зберігає короткі координати коду без повного шляху.
5. Сирі історичні detail/context могли потрапити в перегляд/експорт журналу.
   Вони очищаються під час читання без переписування чи видалення старих рядків.
   Зберігаються коротке пояснення та відбиток; безпечні відбитки не губляться
   після запису й повторного читання.
6. Два аварійні console.error у desktop main більше не друкують сирий Error.

Поведінка запису продажів, приходу, ревізій та оплат не змінювалася.
Не змінено схеми, міграції, права Supabase, налаштування доступу, принтери,
production-акаунти чи наявний механізм завершення процесу.

## Докази

Нові регресії спочатку відтворили витоки/збої на синтетичних даних.
Pino використаний справжній, замінено тільки destination/transport для перехоплення
виводу тестом. Локальні записи перевірялися в тимчасовій SQLite.

Повні повторні прогони:
- web: 131 файл, 1215 успішних тестів, 1 попередній необов'язковий пропуск;
- desktop: 109 файлів, 815 успішних тестів;
- server: 82 файли, 575 успішних тестів;
- разом: **2605 успішних тестів**, на 26 більше попереднього пакета;
- typecheck web / desktop / server / API: успішно;
- lint web: успішно;
- build web / server: успішно;
- git diff --check: без помилок.

Перший паралельний серверний прогін не зараховано: один тестовий процес
завершився на native V8/Wasm assertion
`jit_page_->allocations_.erase(addr) == 1`.
Повтор з `--maxWorkers=1` пройшов повністю (575/575, 77.84 с).
Причину нестабільності тестового середовища цим не встановлено; тестів не вилучали.

Два Chromium UI-набори пройшли:
- AI-input: буфер/Excel, офлайн-розбір, фото-маршрут, невалідна відповідь,
  повтор зі збереженим джерелом, перевірка підсумків, одна чернетка,
  відновлення після запису й перевірка сесії;
- catalog-agent: подвійне натискання, неповна відповідь, повтор,
  одна зміна, зміна магазину/акаунта/ролі та пізня відповідь.

Повтор навантажувального синтетичного прикладу: 899809 символів / 2000 рядків,
worker 103 мс, максимальний виміряний проміжок UI 12 мс,
перевірка й тестове збереження 1442 мс. Це не замір іншого ПК чи робочої БД.

Попередження збірки про великі chunks та змішані імпорти,
а також SSR useLayoutEffect у частині тестів залишаються окремою роботою.

## Межі й наступне приймання

- Старі файли журналів не видалені та не очищені заднім числом.
- Діагностичний експорт не є анонімним: у локальному журналі залишаються
  службові ідентифікатори документів; сервер зберігає дозволені числові метрики.
- Службові поля бізнес-стану на кшталт queue.last_error чи job.error_message
  не є цим журналом і цим пакетом не переписані.
- AST-перевірка охоплює поточні імпортовані logger-виклики runtime-коду,
  а не ручні scripts/seed чи довільні майбутні обгортки.
- Негайний process.exit / native crash може не встигнути скинути останній
  асинхронний запис. Гарантії збереження журналу при фізичному збої немає.
- Живий Gemini, справжні Storage/мережеві відмови, фізичний друк,
  поведінка встановленого EXE і робота двох ПК тут не перевірялися.
- Наступне: підготовка контрольного випуску й узгоджене живе приймання;
  не позначати всі плани завершеними за синтетичними тестами.
